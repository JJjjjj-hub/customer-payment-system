# 成员 B 任务书：回款核销与统计后端

> 字段、主外键、状态、金额 JSON 类型、响应 code、幂等和作废接口统一以 [数据库与接口开发公约](数据库与接口开发公约.md) v1.0 为准。以下早期任务清单中的接口示例有差异时，以公约替代；本文件保留分工与执行顺序。

## 项目约定

- 项目正式名称：客户回款数据库系统；当前用户负责成员 B。
- 业务闭环：客户 → 合同 → 应收款 → 实际回款 → 核销到应收款 → 查看剩余未收金额。
- 技术栈：Java、Spring Boot、MySQL；AI 前端调用统一 REST API。
- 核心表 `customer`、`contract`、`receivable` 由成员 A 设计和创建；你负责 `payment`、`payment_allocation`。先共同冻结字段、外键和接口，再分别编码。
- 金额统一使用 `DECIMAL(12,2)`，Java 使用 `BigDecimal`。所有回款新增和核销写入必须在同一数据库事务中完成。

## 你的职责

负责实际回款登记、回款撤销/更正规则、回款到应收款的核销、余额与回款统计、后端联调测试，以及系统运行和测试分析报告部分。

## 任务清单

### 并行开发边界

不必等待成员 A 完成全部模块。先共同确认客户、合同、应收款的主外键、金额与状态口径和接口字段；约定之后即可用测试夹具建立最小客户/合同/应收数据，独立实现回款、核销、统计及其测试。此时夹具只服务本地测试，不作为正式数据库模型另起一套结构。最终联调依赖 A 提供正式建表脚本和真实应收款接口。

当前没有业务代码，下一步先完成 B1 和 B2 的设计与接口契约；本轮已建立的课程报告材料位于 `../课程报告材料/`。测试结果和运行截图必须在实现后据实补齐。

### B1. 对齐领域规则和接口

- [ ] 与成员 A 一起确认核心表字段、外键、状态命名、统一响应结构和错误码。
- [ ] 采用“回款记录 + 核销明细”分离模型：一笔回款可以分配到多笔应收款，一笔应收款也可以由多笔回款结清。
- [ ] 确认收款可以暂不核销（作为未分配回款），但报表要将未分配余额单独列出，避免把它计为已收清某笔应收款。
- [ ] 确认撤销规则：有核销的回款不可直接物理删除；如需撤销，事务内撤销/删除其核销明细并保留回款状态或审计说明。若课程周期有限，可只实现“禁止删除并提示”。

**交付物：** 将核销规则补入 `docs/需求与规则.md`，并与 A 的接口文档保持一致。

### B2. 实现回款和核销数据结构

- [ ] 编写 `payment` 表 DDL：回款编号、客户 ID、到账日期、回款金额、回款方式、流水号、备注、状态、创建时间。
- [ ] 编写 `payment_allocation` 表 DDL：回款 ID、应收 ID、核销金额、创建时间；设置外键与必要索引。
- [ ] 为重要业务编号设置唯一约束；核销金额大于 0；禁止金额字段使用 `FLOAT`/`DOUBLE`。
- [ ] DDL 与 A 的 `sql/schema.sql` 合并，经双方验证后只有一个正式初始化脚本，避免表结构分叉。

### B3. 实现回款登记、查询和核销

- [ ] 实现回款登记 API，支持一笔回款不核销或同时分配给多笔应收款。
- [ ] 写入前验证：客户有效；被核销应收款属于该客户；回款金额大于 0；单笔回款的核销总额不超过回款金额；应收款剩余余额足够。
- [ ] 使用事务和并发保护（锁定应收记录或使用可靠的条件更新），防止两个请求同时核销造成超额。
- [ ] 回款列表支持客户、日期区间、回款方式、流水号查询；详情展示核销明细和未分配金额。
- [ ] 回款修改限制：有核销记录时，不允许直接降低回款金额到已核销总额以下；修改客户需保证所有核销应收款仍属该客户。
- [ ] 初版可以限制撤销/删除：已核销回款提示先撤销核销或禁止删除，并在文档注明。

**建议接口：**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/payments` | 按客户、日期、方式、流水号分页查询 |
| `POST` | `/api/payments` | 登记回款，可选带 `allocations` |
| `GET` | `/api/payments/{id}` | 回款详情及核销明细 |
| `PUT` | `/api/payments/{id}` | 修改未核销回款或符合约束的基本信息 |
| `POST` | `/api/payments/{id}/allocations` | 对未分配金额增加核销 |
| `DELETE` | `/api/payments/{id}` | 仅无核销时允许，或明确返回不可删除 |

**新增回款请求建议：**

```json
{
  "customerId": 1,
  "paymentDate": "2026-11-11",
  "amount": 5000.00,
  "method": "BANK_TRANSFER",
  "referenceNo": "TXN-20261111-001",
  "note": "一期回款",
  "allocations": [
    { "receivableId": 11, "amount": 3000.00 },
    { "receivableId": 12, "amount": 1500.00 }
  ]
}
```

### B4. 实现汇总查询

- [ ] 提供客户维度汇总：合同总额、应收总额、已核销回款、未收余额、未分配回款。
- [ ] 提供应收款维度余额：`应收金额 - 该应收的核销金额之和`；余额小于或等于 0 为已结清，余额大于 0 且过期为逾期，否则为未收/部分收款。
- [ ] 提供按日期区间的回款趋势或每日汇总，供前端用简单表格或图表展示。
- [ ] 汇总查询覆盖空数据、未分配回款、部分核销、跨多笔应收核销和逾期情况。

**建议接口：**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/reports/summary` | 系统总应收、已核销、未收、未分配回款 |
| `GET` | `/api/reports/customers/{customerId}` | 单客户应收与回款汇总 |
| `GET` | `/api/reports/payments/daily` | 日期区间内每日回款汇总 |

## 与成员 A、AI 前端的协作约定

- A 维护 `customer`、`contract`、`receivable`；B 维护 `payment`、`payment_allocation`。所有 DDL 最终汇总进同一初始化脚本。
- 后端 API 统一前缀 `/api`、JSON 请求/响应、日期格式 `yyyy-MM-dd`、金额两位小数；分页参数统一为 `page`、`size`。
- 前端只调用 API，不拼接 SQL，不以本地计算替代服务端核销校验。
- A 在应收款列表/详情返回 `receivedAmount`、`outstandingAmount`、`status`；B 提供核销写入及汇总 API。字段冻结后变更需同步双方和前端提示词/代码。
- 回款成功返回新回款 ID、核销明细和更新后的余额；业务校验失败返回明确可展示的错误消息。

## 完成标准

- 一笔回款可完整入库，可选择暂不核销，也可核销到多笔属于同一客户的应收款。
- 任意路径都无法超额核销；事务失败后数据库不留部分写入。
- 回款、核销明细、应收余额和统计报表相互一致。
- 自动化测试通过，AI 前端可从登记回款走到余额/汇总变化，演示步骤和报告证据齐备。
