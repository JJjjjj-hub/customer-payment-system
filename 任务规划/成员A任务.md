# 成员 A 任务书：客户与应收款后端

> 字段、主外键、状态、金额 JSON 类型、响应 code、幂等和作废接口统一以 [数据库与接口开发公约](数据库与接口开发公约.md) v1.0 为准。以下早期任务清单中的接口示例有差异时，以公约替代；本文件保留分工与执行顺序。

## 项目约定

- 项目正式名称：客户回款数据库系统。
- 项目目标：维护客户、合同和应收款，登记客户实际回款并核销到应收款，查询未收余额和回款情况。
- 技术栈：Java、Spring Boot、MySQL；前端由 AI 辅助生成，通过双方共同确认的 REST API 调用后端。
- 业务边界：本项目是课程规模的单体 Web 应用。暂不包含银行流水自动导入、发票、复杂审批、短信通知和多租户。
- 金额统一使用 `DECIMAL(12,2)`，Java 使用 `BigDecimal`；日期统一用 ISO 格式 `yyyy-MM-dd`。
- 金额状态以数据库记录和核销明细为准，不直接把“客户收到的钱”当成“某笔应收款已结清”。

## 你的职责

负责前期需求收敛、数据库模型和 DDL，以及客户、合同、应收款三个模块的后端实现；维护系统级接口约定，确保成员 B 和 AI 前端能按同一套字段与规则开发。

## 任务清单

### A1. 定义需求和业务规则

- [ ] 编写精简需求说明：目标用户为财务/业务人员；列出客户管理、合同管理、应收款计划、回款登记、核销、欠款查询、汇总统计等功能。
- [ ] 确认术语：应收款是预计或已到期应收金额；回款是实际到账金额；核销是把回款分配给一笔或多笔应收款。
- [ ] 确认关键约束：单笔回款核销总额不得超过回款金额；应收款累计核销额不得超过应收金额；客户停用不删除历史业务；合同及业务记录优先软删除或限制删除。
- [ ] 写出非功能要求：登录可作为简化版演示（若时间不足则使用单用户模式并在报告说明）；输入校验、错误提示、数据备份与恢复演示。

**交付物：** `docs/需求与规则.md`，供成员 B 和前端实现共同引用。

### A2. 设计并建立数据库

- [ ] 绘制 ER 图，说明客户、合同、应收款、回款、核销明细的基数和关键约束。
- [ ] 设计以下核心表，列名与类型在接口冻结前和成员 B 一起确认：
  - `customer`：客户编号、名称、联系人、电话、邮箱、地址、状态、创建时间。
  - `contract`：合同编号、客户 ID、合同名称/编号、签订日期、合同金额、状态、备注。
  - `receivable`：应收编号、合同 ID、应收金额、到期日、说明、状态。
  - `payment`：由成员 B 实现，回款编号、客户 ID、到账日期、金额、方式、流水号、备注。
  - `payment_allocation`：由成员 B 实现，回款 ID、应收 ID、核销金额。
- [ ] 核心表使用主键、外键、唯一约束和必要索引；金额不使用浮点类型。手机号、邮箱等非必填字段允许空值。
- [ ] 为 `customer`、`contract`、`receivable` 编写可重复运行或明确初始化顺序的 MySQL DDL；提供少量连贯的演示数据。
- [ ] 对关系模式进行规范化说明，至少解释主键、外键、重复数据如何避免，以及金额汇总为何由明细关联计算。

**交付物：** ER 图源文件/图片、关系模式说明、`sql/schema.sql`、`sql/seed.sql`。

- [ ] 实现客户新增、详情、分页列表、关键字查询、编辑、停用/启用。
- [ ] 校验客户名称非空；电话号码、邮箱格式做基础校验；遇到关联合同的客户不允许物理删除。
- [ ] 为 Service 层编写单元或集成测试，覆盖新增、查询、重复/非法输入、停用后历史查询。

**建议接口：**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/customers` | 分页查询；支持 `keyword`、`status`、`page`、`size` |
| `GET` | `/api/customers/{id}` | 客户详情 |
| `POST` | `/api/customers` | 新增客户 |

### A4. 实现合同和应收款模块

- [ ] 实现合同新增、列表、详情和编辑；合同必须关联有效客户，合同编号在系统内唯一。
- [ ] 实现应收款创建、列表、详情和编辑；应收款必须关联合同，金额大于 0，到期日有效。
- [ ] 应收状态建议由核销计算：未收、部分收款、已结清；逾期状态根据到期日和剩余金额派生，不依赖人工误填。

**建议接口：**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/contracts` | 按客户、合同编号分页查询 |
| `POST` | `/api/contracts` | 新增合同 |
| `GET` | `/api/contracts/{id}` | 合同详情 |
| `PUT` | `/api/contracts/{id}` | 编辑合同 |
| `GET` | `/api/receivables` | 按客户、合同、状态、到期区间查询 |
| `POST` | `/api/receivables` | 新增应收款 |
| `GET` | `/api/receivables/{id}` | 应收款详情及核销汇总 |

## 和成员 B 的接口边界

- A 负责 `customer`、`contract`、`receivable` 的结构与读写；B 负责 `payment`、`payment_allocation` 的结构与读写。
- 双方不得自行更改共享字段名或状态含义。数据库迁移或 DDL 有改动时，先同步再实现。
- B 的回款新增接口必须通过事务写入回款及其核销明细；A 的应收余额由回款核销明细汇总得出。
- 统一响应建议：`{ "code": 0, "message": "success", "data": ... }`；分页数据包含 `items`、`page`、`size`、`total`。错误响应使用非零 `code` 和可读 `message`。
- 前端以 API 文档为准，不直接访问数据库，也不自行推导金额状态。

## 完成标准

- 空 MySQL 数据库可按说明成功初始化，外键和唯一约束生效。
- 客户、合同、应收款主要增查改流程能通过接口完成，错误输入有明确反馈。
- 应收款余额与核销明细计算一致；存在核销时，不能通过编辑把余额改成负数或抹去历史。
- 自动化测试通过，报告所需图表、数据字典和截图已归档。
