# 客户回款数据库系统：总体任务完成路径

> 字段、主外键、状态、金额 JSON 类型、响应 code、幂等和作废接口统一以 [数据库与接口开发公约](数据库与接口开发公约.md) v1.0 为准。以下早期任务清单中的接口示例有差异时，以公约替代；本文件保留分工与执行顺序。

## 1. 项目目标和范围

开发一个面向课程演示的客户回款管理系统，形成以下闭环：

```text
客户 → 合同 → 应收款计划 → 实际回款 → 核销分配 → 未收余额与回款统计
```

系统采用 Java / Spring Boot + MySQL。AI 辅助生成前端，前端仅通过 REST API 访问服务端。两位成员都承担后端工作：A 负责需求、数据模型、客户/合同/应收款；B 负责回款、核销和统计。项目先交付能稳定演示的核心流程，再补报告和改善体验。

建议首版不做银行流水自动导入、复杂审批、发票、多租户或高并发财务结算。若教师给出额外要求，再增补范围。

## 2. 核心业务定义

- **应收款**：根据合同建立的应收计划，记录金额和到期日。
- **回款**：客户实际到账的一笔钱，金额独立于具体应收款。
- **核销**：把回款金额分配到应收款。允许一笔回款对应多笔应收款，也允许一笔应收款被多次回款结清。
- **未收余额**：应收金额减去该应收款所有有效核销金额。
- **未分配回款**：实际收到但尚未核销到应收款的金额。应单独展示，不计作某笔应收款已结清。
- **应收状态**：从到期日、应收金额和累计核销额派生未收、部分收款、已结清、逾期等状态；状态规则由后端统一计算。
- **金额规则**：MySQL 用 `DECIMAL(12,2)`，Java 用 `BigDecimal`；回款金额和核销金额必须大于 0；核销总额不能超过回款金额，也不能超过应收余额。

## 4. 推荐 API 和数据边界

### 客户、合同、应收款（A）

- `GET/POST /api/customers`：查询和新增客户；`GET/PUT /api/customers/{id}`：查看和编辑；`PATCH /api/customers/{id}/status`：启用或停用。
- `GET/POST /api/contracts`：合同查询和新增；`GET/PUT /api/contracts/{id}`：查看和编辑。
- `GET/POST /api/receivables`：应收款查询和新增；`GET/PUT /api/receivables/{id}`：查看和受约束编辑。

### 回款和核销（B）

- `GET/POST /api/payments`：查询和新增回款。
- `GET/PUT /api/payments/{id}`：查看和受约束编辑。
- `POST /api/payments/{id}/allocations`：将未分配金额核销到应收款。
- `GET /api/reports/summary`：系统总览；`GET /api/reports/customers/{customerId}`：客户汇总；`GET /api/reports/payments/daily`：每日回款汇总。

建议统一响应为 `{ "code": 0, "message": "success", "data": ... }`；分页使用 `page`、`size`，响应数据含 `items`、`page`、`size`、`total`。日期使用 `yyyy-MM-dd`。应收款列表返回 `receivableAmount`、`receivedAmount`、`outstandingAmount`、`status`。回款写入接口接收客户、到账日期、金额、方式、流水号、备注和可选核销明细。

数据表边界：A 负责 `customer`、`contract`、`receivable`；B 负责 `payment`、`payment_allocation`。A/B 先冻结共享字段和外键，再合并到一份 `sql/schema.sql`。避免双方分别维护相互不兼容的表结构。

## 5. 分阶段完成路径

### 阶段 1：定范围和协作约定

- A 起草角色、功能、非功能要求和业务词汇；B 校核回款、核销、撤销规则。
- 两人确认一期范围、字段命名、状态含义、接口响应、异常格式和 Git/文件协作方式。
- 绘制闭环草图，先确认一个最小演示场景：一个客户、一份合同、两笔应收、一次跨应收回款。

**验收点：** 需求边界和术语统一；不存在“回款金额等于已收应收金额”这类歧义。

### 阶段 2：数据库与 API 契约

- A 画 ER 图并提出核心表字段；B 评审回款与核销模型。
- A/B 一起确认外键、唯一键、金额约束、删除策略和应收余额算法。
- 先写示例 JSON 和 API 字段，再开始并行实现，减少联调时的字段返工。
- 用 DDL 创建表并导入演示数据；从空库完整初始化一次。

**验收点：** ER 图、关系模式、DDL、API 示例互相一致；外键有效，金额精度正确。

### 阶段 3：后端并行实现

- A 实现客户、合同、应收款及列表余额展示需要的查询字段。
- B 实现回款登记、核销事务、回款查询与汇总统计。
- A/B 每完成一个模块先跑模块测试，再合并到共同分支或共享版本。
- 重要金额规则下沉服务端，不能依赖前端校验。

**验收点：** API 可独立调用；正常路径和主要非法输入均有测试。

### 阶段 4：前端 AI 生成与联调

- 将已冻结的 API 契约、字段示例、页面清单和错误处理规则提供给 AI 生成前端。
- 页面建议：客户列表/详情、合同和应收款维护、回款登记/查询、经营总览。
- 先用固定 JSON/mock 完成页面，再逐页切换到真实 API；不要让前端自行计算应收状态。
- A 主验收客户/合同/应收页面；B 主验收回款、核销及统计页面；共同修复接口和显示问题。

**验收点：** 浏览器操作能完成新增客户、创建合同及应收、登记回款、核销、查看余额变化的端到端流程。

### 阶段 5：测试和数据恢复

- 覆盖成功路径：未核销回款、部分核销、单笔回款核销多笔应收、分次回款结清应收。
- 覆盖失败路径：零/负金额、核销超回款额、核销超应收余额、客户与应收不匹配、重复流水号、非法日期。
- 检查事务失败是否完全回滚，并核对报表数字等于明细汇总。
- 导出 MySQL 备份，在空库恢复后重跑关键查询和演示。

**验收点：** 自动化测试通过；备份可以恢复；测试结果有记录和截图。

### 阶段 6：报告、演示和提交

- A 完成需求分析、数据字典、ER 图、关系模式、范式分析和数据库实施章节。
- B 完成应用程序详细设计、测试用例与结果分析、系统运行和回款截图。
- 两人共同整理目录、原创声明、成员分工、参考资料、评分表和源程序说明。
- 按“先客户、合同、应收，再登记回款和核销，最后查看报表”的顺序排练演示；准备一条失败用例展示服务端约束。
- 最终按课程 2026 报告要求检查纸质报告、源程序、SQL 脚本、需求/设计文档和演示环境。

**验收点：** 从干净数据库按 README 能启动系统；演示数据可重复重置；报告目录与实际实现一致。
